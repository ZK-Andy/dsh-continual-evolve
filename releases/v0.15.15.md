<h3 id="cn-v0.15.15">v0.15.15 — 给评审一个「今天」，给诊断一个自己的家</h3>

两件都关于"看不见"的事。**第一件**：自进化环试运行 3 天攒下 114 条 verdict，逐条读完 13 条改写提案，其中 **8 条的拒绝理由都是「正文含未来日期」**——而被点名的 `2026-10-06` / `10-07` / `10-09` 相对当天（10-14）全在过去。查下去发现模型根本没有"今天"这个基准：插件的 LLM 调用是直调（一条 user 消息 + 一份 system），DSH 给正常会话轮注入的日期被这条路径整个绕开，而 rubric 偏偏要判「⑤不过时」，提取提示词还要求把相对日期折算成绝对日期。模型只能拿自己的先验填这个洞，于是把近期过去日期读成未来，顺手把正确的日期删了。本版把基准日作为**每次调用的事实**送进指令侧。**第二件**：一年里第二次撞上同一堵墙——插件写 `ctx.logger` 的诊断在本机不留任何痕迹（宿主没接 exporter，默认只有内存缓冲），而"承接方"在用户环境里、不归我们控制。本版不再指望那条通道：**诊断只写自己的库**，并顺手补上四张账本一直缺失的裁剪触发。

### 问题修复

- **评审与提取提示词补「今天」基准**（@ZK-Andy，`07d9b63`）：新增 `src/prompt-date.ts`（`todayUtc()` 是插件唯一取钟点、`dateBaseline()` 是那行基准的唯一家）；`SubagentCall` 增 `today`，定义表的 `system` 支持构建式 `(context) => string`，装载器按次解析——调用点不做任何拼接。评审复用运行自身的 `opts.day`（硬顶账户的 UTC 日，不新增第二个时钟），提取在环边界取当日。基准行同时声明两侧语义：**早于或等于今天是正常过去事实、不是缺陷、不要据此改写；只有晚于今天才算「未来日期」错误**——保留真问题（记忆里写尚未发生的事）的检出，同时消除误判。六份子代理定义一律带基准；时钟只进 system，不进贴着条目正文的 user prompt（2026-10-14 回抄事故的渠道）。

### 新功能

- **插件自有日志表 `plugin_log`**（@ZK-Andy，`eac6c7c`+`5bef203`）：宿主 logger 开箱没有 exporter（本机实证：`~/.dsh/logs/host.log` 里插件行 0 条），承接方又归用户环境——诊断改为只落自己的库：`createPluginLog` 写 `plugin_log(ts, level, event, message, workspace_id, session_id)`，**不镜像宿主 logger**（插件对宿主日志通道零依赖，`HostContext` 不再声明 `logger`），写失败绝不抛（一行诊断不配让会话倒下）。24 处调用点收敛为「稳定事件名 + 原文 + 归属」——`drain-failed` / `card-no-webserver` / `memory-tools-registered` … 可按事件聚合而不是逐行读；消息上限 2000 字符。回查一句 SQL：`SELECT ts, level, event, message FROM plugin_log WHERE level != 'info' ORDER BY ts DESC`。
- **账本保留期首次接上触发**（@ZK-Andy，`eac6c7c`）：`pruneLedger` 从落地起**没有任何生产调用者**（只在测试里被调用），所以"账本会被裁剪"是 API 的真话、机器的假话——真库 9 天 547 条 `extraction_log`、3 天 115 条 `review_log`。现在 `src/retention.ts` 的 `pruneIfDue` 按 **30 天窗口**、**UTC 日节流**、幂等裁剪四张账本（extraction / skill / review / plugin），触发点三个且都不需要新调度器：store 就绪、写日志时、提取应用后的巡检处。

### 升级提示

- 无破坏性变更。**schema 变更**：新增 `plugin_log` 表与其索引，旧库首次打开自动建表（真库副本实测：写入、镜像语义、裁剪水位、既有账本行数均如预期）。
- dotnet-desktop 是 npm 实体拷贝：更新到 0.15.15 后**重启 App** 即生效（`client/` 本版未动，无需硬刷）。
- 评审环保持试运行（`review.dryRun` 默认开）：本版不改开关、只修基准——修好后的可采纳率要等下一轮 dry-run 复跑再评，那之前不关 dry-run。
- **已知边界**：基准日取 UTC 日（与账户同单位），本机 UTC+8 的凌晨 0–8 点它比日历早一天；两条轨共用同一基准，插件内部自洽。另：store 打不开时诊断无处可写（唯一日志家就是那张表），已记入 ADR。
- 测试 397 → 409；typecheck / lint / 覆盖率（96.41-90.98-100）/ 文档门禁 / `check:pack` 全绿。

<h3 id="en-v0.15.15">v0.15.15 — a "today" for the reviewer, a home for the plugin's own diagnostics</h3>

Both changes are about things nobody could see. **First**: the evolution ring's three-day trial produced 114 verdicts, and reading the 13 rewrite proposals one by one showed **eight rejected on the grounds of "the body contains a future date"** — while the dates named (`2026-10-06`, `10-07`, `10-09`) were all in the past relative to that day (10-14). The model had no "today" to reason from: the plugin's LLM calls are direct (one user message plus one system prompt), so the date DSH injects into ordinary session turns is bypassed entirely — while the rubric asks for a freshness judgment and the extraction prompt asks for relative dates to be written out absolutely. The model filled the gap with its own prior, read recent past dates as future ones, and stripped the correct dates. This release hands the baseline day to every call as a fact, on the instruction side. **Second**: for the second time this year, plugin diagnostics written to `ctx.logger` left no trace on this host (no exporter attached; the default is an in-memory buffer) — and the sink lives in the user's environment, which we do not control. This release stops depending on that channel: **diagnostics go into the plugin's own store**, and the four ledgers finally get the prune trigger they never had.

### Bug Fixes

- **A "today" baseline for the review and extraction prompts** (@ZK-Andy, `07d9b63`): new `src/prompt-date.ts` (`todayUtc()` is the plugin's single clock read, `dateBaseline()` the single home of the line); `SubagentCall` gains `today` and a definition's `system` may be a builder resolved once per call by the loader — no call site composes anything. Review reuses the run's own `opts.day` (the hard cap's UTC day; no second clock), extraction resolves it at its ring boundary. The line states both sides: **a date at or before today is an ordinary past fact, not a defect, and must not be rewritten away; only a date after today is a "future date" error** — keeping the real defect (a memory stating something that has not happened) detectable while removing the false positives. All six subagent definitions carry the baseline; the clock rides the system prompt only, never the user prompt next to the item text (the channel that caused the 2026-10-14 copy-back).

### Features

- **The plugin's own log table, `plugin_log`** (@ZK-Andy, `eac6c7c`+`5bef203`): a stock host attaches no exporter to its logger (established here: zero plugin lines in `~/.dsh/logs/host.log`) and that sink belongs to the user's environment — so diagnostics now land only in the plugin's own store: `createPluginLog` writes `plugin_log(ts, level, event, message, workspace_id, session_id)` and **mirrors nothing to the host logger** (zero dependency on that channel; `HostContext` no longer declares `logger`), never throwing (a diagnostic line is not worth failing a session for). All 24 call sites converged on a stable event slug plus the message and its partition — `drain-failed`, `card-no-webserver`, `memory-tools-registered` … — so runs can be counted and grepped instead of read line by line; messages cap at 2000 characters. Read it back with one query: `SELECT ts, level, event, message FROM plugin_log WHERE level != 'info' ORDER BY ts DESC`.
- **Ledger retention gets its trigger at last** (@ZK-Andy, `eac6c7c`): `pruneLedger` shipped with **no production caller at all** (only tests called it), so "the ledgers are pruned" was true of the API and false of the machine — 547 `extraction_log` rows in nine days and 115 `review_log` rows in three on the real store. `pruneIfDue` in `src/retention.ts` now prunes all four ledgers (extraction / skill / review / plugin) on a **30-day window**, **throttled by UTC day**, idempotently, from three triggers that need no scheduler of their own: store readiness, a log write, and the post-extraction hygiene pass.

### Upgrade notes

- No breaking changes. **Schema change**: a new `plugin_log` table and its index, created automatically when an existing database is first opened (verified on a copy of the real store: the write, the retention watermark and the untouched ledger row counts all behave as specified).
- dotnet-desktop is an npm copy: update to 0.15.15 and **restart the app** (`client/` is untouched, no hard refresh needed).
- The review ring stays in trial mode (`review.dryRun` defaults on): this release changes no switch, only the baseline — the adoptable rate after the fix needs a fresh dry-run round before anyone turns dry-run off.
- **Known boundaries**: the baseline is the UTC day (the account's unit), so between 00:00 and 08:00 local (UTC+8) it is one day behind the calendar; both tracks share it, so the plugin stays internally consistent. And with the store unavailable a diagnostic has nowhere to go — the store is the only log home — as recorded in the ADR.
- Tests 397 → 409; typecheck, lint, coverage (96.41-90.98-100), docs gates and `check:pack` all green.
