<h3 id="cn-v0.17.0">新功能</h3>

- **评审改为事件驱动：时间不再是引擎，只是兜底。** 过去 `review.staleDays`（默认 30 天）的语义是「上次评审超过 N 天就重新排队」，即每条记忆每 30 天必被重审一遍——这是与内容质量无关的固定维护税，记忆越多越亏（1000 条时每天约 33 条纯到期重审）。现在重审由**事件**触发：新记忆落盘时与既有条目字面相近、某条记忆 `corrects` 指向它、用户纠错类 feedback 落在同一主题——任一事件落进新表 `item_events`，条目随即回到队首。事件与正文在同一个事务里写入，因此不会出现「本体已改、牵连丢失」。日历降级为兜底抽样：`staleDays` 现在是**最长免审期**，超过只是「有资格被抽中」，抽样名额取批量的五分之一（至少 1 条），其余名额全给新写与事件。一条记忆连续两次 keep 且其间无事件，免审期翻倍（30→60→120 封顶）；任何非 keep 判词或牵连事件都把它清零——同一条被反复议价、结论来回翻转的日子结束了。(@ZK-Andy) <!-- 0e6bd8b -->
- **评审日账按来源分列。** `review_daily` 新增 `requeued_link`（事件牵连）/`requeued_clock`（日历时钟）/`requeued_sampled`（抽样）三列，`requeued` 恒等于三者之和且由代码求和得出，不由调用方传值——「今天为什么再审了这些条目」现在是一行可读的数字，而不是一个总数。(@ZK-Andy) <!-- b6978b6 -->
- **连带修正「被纠正牵连」的老数据。** 条目被 `corrects` 指向时，即使没有事件行也会进队——本版之前写下的纠正链不会因为换了触发制而从队列里消失。(@ZK-Andy) <!-- b6978b6 -->

<h3 id="en-v0.17.0">Features</h3>

- **Reviews are now event-driven: the calendar is a backstop, not the engine.** `review.staleDays` (30 by default) used to mean "any item whose last review is N days old requeues" — every memory re-reviewed every 30 days, a fixed maintenance tax unrelated to content quality that grows linearly with the store (about 33 pure-expiry reviews a day at 1000 items). Requeues now come from **events**: a drop-in write whose text lands near an existing item, a memory that names another as the thing it `corrects`, or a correction-shaped feedback write on the same topic. Any of them lands a row in the new `item_events` table and puts the item back at the front of the queue. Events commit in the same transaction as the body they describe, so "the text changed but the linkage was lost" cannot happen. The calendar becomes a sampling backstop: `staleDays` is now the *longest exemption window* — past it an item is merely *eligible* to be sampled, the sample slot is a fifth of the batch (one at minimum), and the remaining slots go to new writes and events. Two keeps in a row with no intervening event double the window (30→60→120, capped); any non-keep verdict or linkage event resets it — an item can no longer be re-argued day after day with the verdict flipping each time. (@ZK-Andy) <!-- 0e6bd8b -->
- **The daily review account is split by source.** `review_daily` gains `requeued_link` (event linkage), `requeued_clock` (calendar milestones), and `requeued_sampled` (stale sampling); `requeued` is always their sum, derived in code rather than supplied by the caller, so "why did these items come back today" is a readable number instead of one total. (@ZK-Andy) <!-- b6978b6 -->
- **Old correction links keep working.** An item named by a `corrects` link stays queued even without an event row, so correction chains written before this release do not vanish with the new trigger model. (@ZK-Andy) <!-- b6978b6 -->
