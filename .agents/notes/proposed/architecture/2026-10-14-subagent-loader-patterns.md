# Agent Note: 子代理与装载器（通用子代理 + 模式选型）

Status: proposed

## Problem

插件里所有 LLM 调用都是**调用点内联**的：`src/llm-call.ts` 的 `streamOnce` 是唯一底层直调，feature 代码（`src/review.ts`、`src/extraction.ts`）直接 import 它，并在调用点写死身份、提示词与限制。

| 直调点 | 身份 | 内联在调用点的东西 |
|---|---|---|
| `review.ts` 便宜门 | 评审便宜门 | `REVIEW_CHEAP_SYSTEM_PROMPT` + `GATE_MAX_TOKENS` |
| `review.ts` 昂贵门 | 评审昂贵门 | `REVIEW_MEMORY_SYSTEM_PROMPT` / `REVIEW_SKILL_SYSTEM_PROMPT` + `EVOLVE_MAX_TOKENS` |
| 提取轨预检门 | 提取便宜门 | `EXTRACTION_CHEAP_SYSTEM_PROMPT` + `CHEAP_INCREMENT_MAX` |
| 提取轨主调用 | 提取 | `EXTRACTION_SYSTEM_PROMPT` |

三条后果：

1. **"有几个子代理、各自是什么"从代码里读不出来**。实际发生：四个岗位只写了三份说明书——技能便宜门缺位，被记忆门的说明书顶替，`ts-standards` 因此被拒 5 次（模型照着"你是记忆库的内容评审门"判，不是判歪）。
2. **记忆与技能共用一条轨**，而两者的家规相反（记忆要求"抹掉仓库名还成立"，项目技能要求"绑仓库"），只能靠 prompt 散文分支维系——`review.ts` 两处一个带 kind 分支、一个不带，漏点由此而来。
3. **加一份子代理、改一处限制，都要动调用点**；限制（预算/输出解析/路由）散落在各调用点，无法一处审阅。

## Proposal

- **通用子代理**：一个执行器，只做"跑一次带提示词 / 工具 / 限制的任务"。身份、提示词、工具、限制、输出解析全部是**数据**，来自装载的那份定义，不是代码分支。
- **装载器**：子代理只能**经装载器调用**，feature 代码不再 import `streamOnce`。
- **范围**：插件内所有直调——评审环的门与昂贵门、提取环的预检门与主调用，以及 `streamOnce` 自身，全部收进装载器之后。
- **并入的账本观测缺口**（原独立待办「门失败行补 usage + model 列」）：
  - 记账是执行骨架的固定一环，**失败路径同样执行**——调用抛错前已观测到的 usage / finish / route 随失败行落账（`streamOnce` 在 error / 空文本分支抛错，已观测到的 usage 就此丢弃）。
  - `review_log` 增加 `model` 列，与 `extraction_log` 对齐；同时修掉提取轨 `llm-failed` 行 `model` 恒空——两轨同一个抛出点。
  - 门预算改为**按模型能力推导**（与既有的推理档位推导同源），把「同一模型同一预算间歇撞 max-tokens」从设计层消掉。
  - 判据：账本能直接回答「某次门失败跑在哪个模型、烧了多少 token」，不必回捞宿主日志。
- **模式选型**：
  - **装载 = 策略模式 + 简单工厂**：一份子代理定义 = 一个策略（提示词/工具/限制/解析），装载器按任务取用。即"策略 + 简单工厂"的融合用法——工厂只负责实例生产，策略负责行为封装与切换。
  - **通用子代理的执行骨架 = 模板方法**：装配 → 调用 → 解析 → 记账固定，差异全部由策略注入。
  - **流程推进（门 → 昂贵门 → 落盘/终止）= 责任链**：各环节职责单一、互不依赖，由环境类组装链条，请求沿链传递直到某环处理或终止。
  - **定义清单 = 表驱动 / 注册表**：所有子代理定义声明在一处，可读、可加、可改而不牵动别处。
- **边界**：不用状态模式做装载（那是策略的活）；不用策略做流程推进（策略不会自动迁移）。

## Alternatives considered

- **每个门一个子代理（维持现状）**：落败——身份与限制内联在调用点，"有几个子代理"读不出来；加一个岗位就漏一份说明书，已经发生（技能便宜门）。
- **用状态模式管流程**：落败——状态模式要求各状态在**编译期**就知道下一个是谁（迁移写死，等价 if/else-if），而环节需要增删；迁移写死正是现有 `kind === "memory" ? A : B` 硬编码分支的成因。责任链把"谁接谁"交给环境类组装，才容得下增删环节。
- **继续按 kind 在 prompt 散文里分支**：落败——无任何机械约束保证那句分支被读到、被执行。`f43d0ed` 只在昂贵门加了一句"项目技能绑仓库不是缺陷"，便宜门就漏了。
- **只把提示词抽成常量、不引入装载器**：落败——解决不了"直调"与"限制内联"，也读不出一份完整定义。
- **把账本缺口留作独立小改（先补列，再判 max-tokens 根因）**：落败——缺陷在同一个抛出点、两轨同病（评审轨失败行 usage 全空，提取轨 `llm-failed` 行 `model` 全空），独立小改要动同一处两次；判根因所需的样本又只能等环重开才产生。并进返厂一次做完。
- **不落 route / usage，只靠失败行已有的 finish 文本归因**：落败——文本只区分 max-tokens 与 error，答不了跑在哪个模型、烧了多少，正是当前判不出根因的原因。
- **不动（保持 dry-run 静默）**：落败——结构性错误不修，下次会话会继续按层打补丁。

## Consequences

- 加/改一份子代理只动定义，不动调用点；"有哪些子代理"在一处可读。
- 门与昂贵门各自装载自己那份说明书——"四个岗位三份说明书"这类错位结构性消失。
- 所有直调经装载器后，路由解析、推理档位、失败记账、用量留痕收在一处（不再散在调用点）。
- 失败行自带 usage 与 route：门失败率可按模型、按预算下钻，「先补列再判根因」这类取证不再需要。
- 代价：一次跨模块返厂（`src/llm-call.ts`、`src/review.ts`、`src/extraction.ts`、`review_log` 的列迁移及其测试），随下一批发版；本笔记取代按层修法的旧笔记 [2026-10-12-content-quality-evolution](../../implemented/architecture/2026-10-12-content-quality-evolution.md) 与 [2026-10-12-review-scope-and-dryrun-proposals](../../implemented/architecture/2026-10-12-review-scope-and-dryrun-proposals.md) 中关于分层修补的部分，并取代独立待办「门失败行补 usage + model 列」。
