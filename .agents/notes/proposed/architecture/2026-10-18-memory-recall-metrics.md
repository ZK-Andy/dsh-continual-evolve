# Agent Note: memory-recall-metrics

Status: proposed

> 放置路径：本文件（`.agents/notes/proposed/architecture/2026-10-18-memory-recall-metrics.md`）。
> 2026-10-18 用户提出「记忆召回率没有统计、看起来偏低」，同日调研四个成熟开源项目后落成本方案；实现前不改代码。

## Problem

**召回率没有被统计，卡片上的数字还被叫错了名字。** 现状三件事：

1. **卡片把"正文取回率"叫成召回**。`injection_log` + `memory_usage` 算的是「注入之后正文被按 id 取回的比例」（`services/injection-stats.ts`）。这只度量 adoption，不度量 recall：规则型记忆（如 `release-only-after-ci-green`）的钩子本身就是可执行规则，不取正文也照样生效——「被读 0%」是好现象，不是坏信号。
2. **样本小到不能看**。`injection_log` 随 v0.19.0（2026-10-18 11:44）落地，7 天内只有 1 行（本会话）；同一窗口内实际有 69 个会话。卡片显示「注入 14 / 被读 0（0%）」，看起来像召回崩了。
3. **离线召回基线只是冒烟**。`npm run eval:recall` 有 5 条记忆 / 9 条查询，报 hit@1 与 MRR；没有覆盖检查（哪些记忆从未被任何查询命中）、没有负例、没有 recall@k。

用户据此判断"全局那几条特别是发版那条召回率应该更高"，而真实情况是：全局 4 条**每个工作区每次会话都注入**（索引召回 100%），发版规则今天确实生效（问版本号等批准），只是正文一次没被取。

## Proposal

分三步，C 最便宜先做，A 次之，B 看 A 的数字再定。

### C. 命名与样本守卫（约 30 分钟，无 LLM 成本）

- 卡片读数改为「**索引召回 N/M** · **正文取回 K**」，把两个概念拆开；`injection-stats.ts` 的 `rate` 改名 `readThrough`（读侧含义）。
- 会话样本 < 10 时显示「样本不足（N 个会话），暂不显示比率」，避免单会话样本被当成趋势。
- 索引召回分母 = 库内该分区 active 记忆（含合并后的全局 L0），分子 = 本次注入点名的条数；两者的差就是预算三档降级吞掉的条数。

### A. 扩 fixture + 逐条覆盖报告（约半天，零 LLM 成本，进 CI）

- fixture 覆盖每类记忆：`user` / `feedback` / `reference` 各 ≥2 条，并包含 4 条全局 L0 中的至少 2 条（发版规则必须在其中）。
- 加**负例**：明显不该召回的查询（如"今天天气"），断言 hit@1 不命中。
- `eval:recall` 输出从单一 hit@1/MRR 扩为：recall@1、recall@3、逐条覆盖（哪条记忆从未被任何查询命中，红色列出）、负例误命中数。
- 进 CI：召回退化即红。

### B. 小规模端到端（约 1 天，每次运行几分钱，手动触发）

- 从真实会话轨迹抽 30–50 个问题，人工标注证据记忆 id（LongMemEval 的 `has_answer` 思路），存 `test/fixtures/recall/qa.json`。
- `npm run eval:qa`：检索 → answerer 用 flash 作答 → judge 对 evidence 判分，产出「准确率 / 召回率 / 每次消耗 token」三个数。
- 手动触发，不进 CI（有 LLM 成本与判分波动）。

### 明确不做

- **不把"正文被读次数"当召回率**：它是 adoption 遥测，保留但改名，不参与召回判定。
- **不建通用"行为命中率"**：无便宜算法，成熟项目也不做；行为类知识交给 B 的 QA 题覆盖。

## Alternatives considered

- **沿用现状、只把文案说清楚**：卡片仍然只有 adoption 一个数，召回空洞（某条记忆从未被任意查询命中）永远看不见。落败原因：解决不了"召回率是多少"这个问题本身。
- **直接上 LOCOMO / LongMemEval 全量**（500–2000 题 + 外部 judge）：行业标准，但依赖外部数据集与稳定 judge，单人插件的记忆只有十几条，全量题目的绝大部分与我们无关。落败原因：成本与规模严重不匹配；先自建小集，跑通后再考虑对照公开集。
- **只做端到端 QA、不做检索召回**：能给出"准不准"，但检索错和回答错分不开，退化时无法定位。落败原因：两层要分开报，LongMemEval 自己的设计也是 turn/session recall 与 QA accuracy 并列。
- **通用行为命中度量**（自动判断会话是否遵守某条记忆）：无便宜且可靠的算法，成熟项目也没有。落败原因：会变成第二套评审环，成本高于收益。
- **把"被读数"直接改名为"召回"就算了**：概念仍然混着，用户会继续误判"规则没被召回"。落败原因：词与定义不符比没有指标更糟。

## Acceptance criteria

- 卡片同时显示「索引召回 N/M」与「正文取回 K」，且样本 <10 时比率位置显示样本不足提示。
- `npm run eval:recall` 输出 recall@1 / recall@3 / 逐条覆盖 / 负例误命中，CI 在召回退化时失败。
- （B 落地时）`npm run eval:qa` 一条命令产出准确率与 token 成本。

## Risks

- **自建 fixture 有作者偏差**：查询由我们写，容易只覆盖"我们知道怎么写得到"的问法；缓解方式是 B 的问题从真实轨迹里取。
- **改名有认知成本**：卡片读者要重新理解两个读数；用同一屏的短说明抵消。
- **A 的覆盖报告可能立刻红**：若某些记忆确实零查询命中，CI 会一直红——落地方案必须同时补查询，而不是关掉断言。
