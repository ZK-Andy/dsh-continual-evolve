# Agent Note: 经典分层＋通用仓储——统一读写工具与描述符式扩展

Status: implemented

## Problem

插件没有数据层：存储、门禁、投影、账本摊在功能代码里，新增一类管理对象只能水平复制。实测（2026-10-15）：`src/store.ts` 1635 行（规范上限 400，无豁免）；59 处 `database.prepare` 中 `skill*` 18 条是无前缀那套逐条加前缀的复制；12 个文件躺着同名镜像；`run-gates` 五项全是文档侧，没有任何脚本量 `src/` 规模。设计里的 harness 状态有四类（提示词补充 / 记忆 / 技能 / 子代理规格），只落地两类——第三类进来会再抄 12 个文件。

## Decision

采用现成架构，不自创：**经典分层（表现层 / 应用服务层 / 数据访问层）＋通用仓储**（Service Layer + Repository + Transaction Script）。表现层只做翻译与渲染（工具注册、卡片路由、注入、投影物化），应用服务层做门禁组合与提案落盘，数据访问层做连接/事务/迁移与通用仓储；`index.ts` 仍是唯一组装根，依赖单向。

通用仓储按"表名 + 列 + 规则"参数化，底层 `memories` / `skills` 两张表不动，不迁数据、不重建 FTS。模型可见工具收敛为**一个读、一个写**：`evolve_write(kind, action, …)` / `evolve_read(kind, …)`，旧四个工具留一版薄垫片后删除。自创技能一律 `evolve_*` 前缀进 repo，DB 只放运行时沉淀。`src` 规模预算搬上机器门禁（`verify-src-budgets`），`store.ts` 拆解至 ≤ 400 行。

## Alternatives considered

- **完整领域架构（接口 + 每资源实现 + 领域事件）**：单存储/单进程/对象同构，接口永远没有第二个实现；无跨聚合事务与领域事件。落败：仪式成本 > 收益。
- **自创描述符框架（ResourceSpec，2026-10-15 上午版，已废）**：业界无此物，等于把 DDD 拆碎重拼。落败：用户否决，方案文件已删除。
- **只合并物理表与工具（不补层）**：抄写仍在快照/卡片/门禁/投影里。落败：治标不治本。
- **物理并表（`resources(kind, …)`）**：`type`/`corrects` 已是记忆专属列，硬并违反"约束即门禁"纪律；将来分叉更大。落败：2026-10-15 用户否决。
- **继续现状（新增对象继续水平复制）**：`store.ts` 每类 +500~700 行的实测轨迹。落败。
- **统一工具命名备选（沿用 `memory_write`）**：语义偏记忆。落败：采用 `evolve_*`（插件前缀，不撞宿主 `skill`）。

## Consequences

- 代价：P0–P6 六阶段迁移；旧工具一版垫片期；`store.ts` 拆解期 diff 大；`check:docs`/CI 在 P4 完成前对 `store.ts` 保持红灯（门禁有效的证明，不是可忽略的失败）。
- 收益：新增一类对象只加仓储参数 + 服务 + 接线，不再碰 12 个文件；文件预算可执行；内容写作规范（`evolve-skill-creator`/`evolve-memory-creator`）有地方放。
