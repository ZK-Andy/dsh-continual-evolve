# Agent Note: 评审事件制与记忆分层同批实施的队列决策表

Status: implemented

> 放置路径：`.agents/notes/implemented/architecture/2026-10-17-review-and-tiering-batch-rollout.md`
> 讨论来源：2026-10-17 会话（用户问两份提案能否一批做，拍板「执行」）。
> 上游提案：[事件驱动评审](2026-10-16-event-driven-review.md) 与 [记忆分层与两级试用提级](2026-10-13-memory-tiering-and-promotion.md)；本文只裁决两者的共享面、实施顺序与批次边界，不复述各自设计。
> 落地：A1–A4 随 **v0.17.0**（`0e6bd8b`+`b6978b6`），B1–B5 随 **v0.18.0**；两份上游提案同时转 implemented。

## Problem

两份提案各自完整，但共享三处代码面，分开实施会把同一段代码改两遍并留下两套口径：

1. **存储形状**：评审状态（`reviewStateOf` 返回的 `lastTs/evolveCount`）、记忆行（`memories` 的 `status` 枚举与待提级标记）由两者共同扩展——分开做就是两次迁移、两个版本各自带一次表重建。
2. **队列构造**：`collectCandidates` 今天只有三档（新写 / corrects 牵连 / 到期），事件制要重写档位语义，提级要再塞入「提级候选」「实习到期」两类——这是全仓评审侧最容易冲突的一段排序。
3. **口径**：`review_daily.requeued` 两份提案都要改定义（事件制要求 ≈ 牵连+抽查，提级会往队列里加时钟源）——同一指标不能有两个定义。

更关键的是**两者在「何时该重审」上给出互斥答案**：事件制说「连续 2 次 keep 且其间无事件即免审 30→60→120」，提级说「`person` 候选在下一回炉周期必须做第二次独立判定」。没有裁决书，实施时必然在这两条之间来回改。

## Decision

### 批次形态：一个实施窗口、两版发布、八次提交

不合并为单个 commit（单测失败无法定位、桌面端验收一次要看八项、回滚粒度太粗），也不拆成两个独立批次（见 Alternatives）。每个阶段自带回归测试，两版各自行为完整：

**A 版（事件驱动评审，v0.17.0）**

| 阶段 | 内容 | 完成判据 |
|---|---|---|
| A1 存储与形状 | `item_events` 表（牵连事件，事件类白名单单一家 + schema guard 条目）、`review_daily` 分来源计数列、`reviewSettled`（派生 keep 连击）与事件队列读口的 store 表面 | 老库打开幂等：列/表齐全、二次打开零变更；事件写入与行落盘同事务 |
| A2 事件发出 | 落盘成功后按同分区 FTS 相似与 `corrects` 写事件（`similar` / `corrects` / `correction`） | 一次新建牵连同主题旧条目；评审自身的 rewrite 不产生事件 |
| A3 队列 | `collectCandidates` 换成单一决策表（见下）、抽查配额、免审倍数；`staleDays` 语义降为「有资格被抽中」 | 三源优先级与豁免边界单测；无事件时队列只剩抽查 |
| A4 账目与收口 | `requeued` 拆 `link/sampled/clock` 三列且合计恒等于 `reviewed-newItems`；ADR 转 implemented | 分来源计数与总和恒等单测；553+ 测试全绿 |

**B 版（分层与提级，v0.18.0）**

| 阶段 | 内容 |
|---|---|
| B1 存储 | `memories.scope`（`project`/`person`）、`memories.probation_until`、`review_log.verdict` 白名单扩到 `archive/promote/demote`（随 schema guard 条目重建） |
| B2 提取侧 | 提案 `scope` 字段与记忆侧全局写入路径（`GLOBAL_WORKSPACE`） |
| B3 评审出口 | `archive` / `promote` / `demote` 三出口及各自门槛（归档「零引用 + 两次独立判定 + 未被 corrects 引用」） |
| B4 提级事务 | 全局建行 + 项目行归档单事务、30 天实习复审三出口、`memory_write` 手动提级 |
| B5 表现层 | 注入 L0 优先与「试用中」标记、卡片「导出建议」标记 |

### 队列单一决策表

队列在每次 drain 时从库里重建，按来源分档，**同档内**按到期先后（牵连/时钟）或最久未审（抽查）排序：

| 档 | 来源 | 触发条件 | 受免审倍数额免 |
|---|---|---|---|
| 0 | 新写 | 无任何终局判词行，且不是实习行 | 否 |
| 1 | 事件 | `item_events` 有行且其 `ts` 晚于该条目最近一条终局判词 | 否 |
| 1 | 时钟·实习到期 | `probation_until <= now`（B 版起） | 否 |
| 1 | 时钟·提级候选 | `scope = 'person'` 且记录时已判过一次，等第二次独立判定（B 版起） | 否 |
| 2 | 抽查 | 陈旧（`updated_at` 早于 `staleDays × 倍数`） | 是（倍数即豁免） |

免审倍数由派生 keep 连击决定：连击 < 2 → 1×；2–3 → 2×；≥ 4 → 4×（封顶）。连击定义为「最近一次重置点之后连续的 keep 终局判词数」，重置点取 `max(最近一条非 keep 终局判词, 最近一条事件)`——事件或任何非 keep 判词都清零。

抽查名额上限 = `max(1, floor(batchSize / 5))`，其余名额给 0/1 档：事件多时抽查让位，事件少时老条目也不会被饿死。`staleDays` 的新语义是「最长免审期」——超过即有资格被抽中，不再保证全审。

### 四裁决

- **R1 免审倍数不覆盖时钟源**：提级候选与实习到期按日历到期即入队，不受 keep 连击加成。否则 `person` 候选两次 keep 后要等 60 天，第二次独立判定永远等不到。
- **R2 搬迁与评审自身改写真不产生事件**：提级/降级/归档是系统搬运，在目标分区写一条 `promote`/`demote` 判词行作为「已判」凭据（既不产生事件，也不会被当成新写）；评审落地的 rewrite 也不再牵连邻居。只有新知识落盘与 `corrects` 关联产生事件——否则刚判完的条目会被自己的改写立刻拉回队列。
- **R3 时钟源独立于事件与抽查**：实习到期、提级候选不看 `staleDays`、不看抽查配额，它们是第三类源而不是陈旧的一种。
- **R4 事件只由 create 与带 `corrects` 的写产生**：update（含评审 rewrite、手动补写正文）不牵连邻居。

## Alternatives considered

- **单 commit 一次做完**：回滚粒度最粗，单测失败无法定位到面，桌面端验收一次要判八项。落败原因：验证成本高于收益。
- **拆成两个独立批次（先提级、后事件制）**：迁移做两次、`collectCandidates` 重写两次、`requeued` 口径二次改名，且 R1 冲突要在第二个批次重新裁决一遍。落败原因：同一段代码改两遍，且冲突不因拆批消失。
- **只做提级、无限期推迟事件制**：全量重审是 O(N/30) 的固定税，提级正是要把 N 养到上千，先做提级等于先给这条路装上税。落败原因：与既定目标直接冲突。
- **用配置开关灰度（先关豁免、再打开）**：多一个状态位、多一套口径，而 A3 在没有豁免倍数时本身就是安全的（等于多审几遍），不需要开关。落败原因：引入无行为收益的状态。
- **把 `settledStreak` 物化成列**：判词与事件都会重置它，物化就需要两处同步写、一处漏写即漂移；保留期裁剪还会让它与实际判词脱节。落败原因：派生读的成本（每次 drain 一次）远低于双写的一致性风险。

## Consequences

两版落地后，本包的全部行为都由这一张决策表解释；以下是落地时确认的验证与保留的代价。

- **验证**：队列行为单测覆盖档位顺序（新写 > 事件/时钟 > 抽样）、连击倍数边界（0/1 → ×1、2–3 → ×2、≥4 → ×4）、事件清零连击、时钟源不被倍数压制（§R1）；`review_daily` 三列之和恒等于 `reviewed - newItems`；老库迁移幂等（`item_events`、三列与 `review_log` 白名单二次打开零 DDL 变更）；`dryRun=true` 下事件与队列照常记账但零落盘。
- **抽查覆盖率**：N 大时 20% 名额的覆盖慢（1000 条陈旧条目、每天 100 预算约 15 天一轮）——事件是主入口，抽样只作对冲；可观测项进 OBSERVATION。
- **派生连击依赖 `review_log` 保留期**：裁剪后连击归零，条目会更早重审（保守方向，不会漏审）。
- **A 版期间**「时钟源」两档不存在：A 版队列只有 0/1(事件)/2(抽样) 三源，B 版点亮时钟两档——分批发布因此各自行为完整，不需要灰度开关。
- **技能侧只有 `corrects`/`correction` 形状的事件**：技能没有相似度牵连（评审侧 neighbor 提示仍是独立通道），后续再评估是否补。
