# Agent Note: 评审与提取提示词补「今天」基准

Status: implemented

> 证据来源：2026-10-12 起 dry-run 试运行累计 114 条 verdict 的逐条分类（2026-10-14）。

## Problem

试运行 3 天 114 条 verdict：`keep` 71 / `rewrite` 13 / `skip` 29 / `quarantine` 1。逐条读 13 条 `rewrite` 的 `reason` + `proposed` + 现存正文：

| 类别 | 条数 |
|---|---|
| 可原样采纳 | 1 |
| 理由成立但拟改稿有害 | 1 |
| 正确但低价值 | 1 |
| 误判 | 10 |

误判集中在一个形态：**8 条以「正文含未来日期」为由**（点名 `2026-10-06` / `2026-10-07` / `2026-10-09`），而这些日期相对当天（2026-10-14）都在过去。另 1 条是幻觉（声称正文混入评审提示语，而该条正文自 10-11 未改），1 条主张把本机绝对路径「泛化」，而该条记忆的价值恰恰就是本机路径。机制本身有效：3 条真问题都是人容易漏掉的——把用户的一句反问升格为既定事实、钩子与正文自相矛盾、正文夹带瞬态状态。

根因是**直调不带时钟**，不是模型能力问题：

- `streamOnce`（`src/llm-call.ts`）发出去的只有两件东西——定义表里的 `system` 与一条 user 消息，没有 runtime context、没有时间戳。DSH 给正常会话轮注入的日期被这条直调路径整个绕开。
- 评审的 user prompt 逐行只渲染 `id / scope / title / 钩子 / 全文` 与同类候选（`src/review-prompt.ts`），条目自己的 `created_at` / `updated_at` 从不进 prompt——尽管 `collectCandidates` 为了算 staleness 已经解析过 `updatedAt`。
- 而 rubric 要的正是时间相对判断：记忆五维里的「①准确」「⑤不过时」。要 now 却不给 now，模型只能用自己的先验填洞，把近期过去日期读成未来。
- 同病的第二处：提取提示词要求「相对日期一律转成绝对日期（"周四"→"2026-10-08"）」，同样没有基准日可折算。

`rewrite` 是当前唯一把误判变成实际伤害的通道（拟改稿会删掉用户刚立的硬规则），而 dry-run 关停的前置正是可采纳率——噪声直接挡在放权门口。

## Decision

- 新增 `src/prompt-date.ts`：`todayUtc()` 是插件里唯一的取钟点（UTC 日），`dateBaseline(today)` 是那句基准行的唯一家。基准行同时声明两侧语义——**早于或等于今天是正常的过去事实、不是缺陷、不要据此改写；只有晚于今天才算「未来日期」错误**——让「不许写未来日期」这条规则仍然有效，而不是退化成「不许碰日期」。
- 基准日是**每次调用的事实**：`SubagentCall` 增 `today`。定义表的 `system` 可以是 `(context) => string` 构建式，装载器就地解析（`({today}) => 指令 + 基准行`），调用点不做任何拼接——`system` 保持「这份工作的整份指令」这一含义。
- 六份定义一律接 `withDateBaseline`：凡读条目正文的岗位都拿到同一行，环内两个岗位不会对「今天」有各自的理解。
- 两个环各自在自己的边界给出这个事实：评审用它已有的 `opts.day`（硬顶账户的 UTC 日，调度器传 `todayUtc()`），不新增第二个时钟；提取的 `RunOptions.today` 可选，缺省在 `extraction-ring.ts` 组装 `SubagentCall` 处取 `todayUtc()`。
- 日期基准行只进 `system`，不碰 user prompt：贴近条目正文的指令文本会被回抄进改写正文（`afb6b89` 的教训），时钟是指令、不是内容。
- dry-run 保持开启：13 条里只有 1 条可原样采纳，放开落盘会造成真实伤害。评估口径固定为四类（可采纳 / 理由成立但拟改稿有害 / 正确但低价值 / 误判），修好基准后复跑一轮再评可采纳率。

## Alternatives considered

- **把日期行放进 user prompt（条目正文上方）**：落败——正是提示语回抄事故的渠道；`afb6b89` 之后 `evolvePrompt` 的纪律是「`全文：` 之后什么都不许挂」，时钟同理不该贴着正文。
- **给定义加布尔开关、由装载器拼装那句措辞**：落败——提示词措辞搬进执行骨架，且下一份需要时钟的岗位无法用自己的措辞表达自己的时钟语义。
- **只在昂贵门注入**：落败——同一环里两个岗位对同一条目持有不同时间感，「今天」退化成岗位私有知识。
- **只加一句「不要把过去日期判成未来」**：落败——根因是缺基准，模型仍按自己的先验判断，误判照旧；而且禁掉日期判断会放过真正的时间错误（本次 3 条真问题之一）。
- **把日期判断从评审职责里删掉**：落败——会放过「记忆里写了尚未发生的事」这类真实缺陷。
- **换更强的评审模型**：落败——成本更高，且不解决「提示词里没有今天」这一信息缺失。
- **用本地日历日做基准（与用户观感一致）**：落败——硬顶账户按 UTC 日、调度器传的 `opts.day` 即 UTC 日；基准改用本地日会在插件里造出两个「今天」。
- **只修一条轨（只评审或只提取）**：落败——两轨同病（评审判未来日期、提取要求相对转绝对却无参照），分两次改要动同一处两遍。
- **先按现有拟改稿手工挑几条落盘**：落败——人工替环做决策，等于绕过 dry-run 的意义（看清误伤率再决定是否放权）。

## Consequences

- 六个岗位的每条 system 末尾都带基准日，由测试锁死：缺一个岗位、或把它挪进 user prompt，都会红。
- 评审的 `today` 与硬顶账户同源（`opts.day`），插件里只有一个时钟；提取未指定时取运行边界墙钟。
- 已知边界：基准日是 UTC 日，本机（UTC+8）凌晨 0–8 点时它比用户日历早一天。两条轨共用同一基准，插件内部自洽；差异只影响「今天」边界附近那几个日期的观感。
- 代价：一次跨模块变更（新增 `src/prompt-date.ts`，动 `src/subagent.ts`、`src/subagent-defs.ts`、`src/review.ts`、`src/extraction.ts`、`src/extraction-ring.ts` 及其测试），随下一批发版。`todayUtc` 从 `src/review.ts` 迁到新模块（原文是「硬顶账户的 UTC 日」，现在两轨共用）。
- 试运行观察的判据不变，仍是分类口径下的可采纳率；本笔记不关 dry-run。

## Testing

- `test/subagent.test.ts`：构建式 `system` 拿到调用的 `today`（字符串式原样透传）；六份定义逐一断言带基准行与「只有晚于今天的日期」。
- `test/review.test.ts`：一次批次里门与昂贵门两次调用的 system 都带 `今天是 <opts.day>`，且 user prompt 里不含该日期（时钟不进内容通道）。
- `test/extraction.test.ts`：指定 `today` 时预检门与主调用都带它；未指定时取 `todayUtc()`。
